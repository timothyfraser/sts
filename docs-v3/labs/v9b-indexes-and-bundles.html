LC 01 · observe
Query "one station, all time" in Postgres with no index. How many rows are scanned?

      

      
Read "rows scanned" in the sidebar, and look at how many blocks light up.

      
5,191,203. Without an index Postgres cannot know where station A32010's rows are, so it reads all 38,171 pages to find its 103,398 rows.

    
LC 02 · intervene
Switch to "one month, all stations". Add the index, then partition by month. Which change helps this query more?

      

      
The index is on start_code. Does this query filter on start_code?

      
The partition. The index on start_code leaves the scan at 5,191,203 rows, because the query filters on day. Partitioning by month prunes the scan to the 131,483 rows of 2019-09 (967 pages instead of 38,171).

    
LC 03 · transfer
Why does DuckDB read fewer bytes for SELECT sum(trips) than Postgres, and when would you still choose Postgres?

      

      
Pick "All-time totals" and flip the engine. Which column stripes light up in the column store?

      
A row store reads whole rows, so the sum reads all 312,696,832 bytes of pages; the column store reads only the 4-byte count values, 20,764,812 bytes. Postgres still wins for a live app that inserts and updates single rows and looks one up by key.
