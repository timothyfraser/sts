LC 01 · observe

In the denormalised table, tick "Rename airline EV". How many cells change?

Read "cells changed" in the sidebar, and count the highlighted cells in the airline column.
12. The name is copied onto each of the 12 EV flights in the sample, so the UPDATE touches 12 cells. Switch to Normalised and the same rename touches 1 cell in airlines. Miss one of the 12 and the table disagrees with itself: an update anomaly.

LC 02 · intervene

Switch to Normalised, tick "Enforce foreign keys", then add the flight with carrier ZZ. What does the database do?

Compare "insert" and "rows (flights)" with the foreign key off and on.
It refuses. Postgres says ERROR: insert or update on table "flights" violates foreign key constraint; SQLite says FOREIGN KEY constraint failed. flights stays at 40 rows and orphans at 0. With the key off, the row goes in and becomes 1 orphan that no join can name.

LC 03 · transfer

The base tables are normalised. Why do analysts often build a denormalised view on top for a dashboard?

Compare "bytes" in the two designs, then read the last lines of the code panel in the Normalised design.
The wide table is bigger (3,854 bytes against 2,607 here), so storage is not the reason. A view is the join, run on demand: the dashboard reads one table with no joins, while every edit still lands once in the keyed base tables.
