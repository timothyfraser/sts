LC 01 · observe

At baseline (directed, weight 1 or more, AM + PM), how many unique directed edges are there?

Read "edges" in the sidebar, not "tally rows". count(from, to) collapses many day-by-day rows into one row per pair.
487. The 1,886 tally rows (one per start, end, day and rush period) collapse into 487 distinct (from, to) pairs; 138 of the 625 possible ordered pairs never saw a ride.

LC 02 · intervene

Switch to Undirected. Which edges merge, and what happens to the counts?

Watch "edges" and "rides" together. pmin(from, to) and pmax(from, to) put both directions of a pair under the same key before count() adds them.
Each pair A→B and B→A becomes one row with the two weights summed, so edges drop from 487 to 292 while rides stay 14,402. Self-loops (rides back to the same station) cannot merge. The matrix becomes symmetric, so filled cells rise to 559: every undirected edge fills two mirror cells.

LC 03 · transfer

At 500 stations, why would an adjacency matrix be a poor way to store the network in Postgres?

Compare "matrix bytes" with "edge list bytes", and note that matrix size grows with nodes squared while the edge list grows with the edges that actually happened.
Here 25 busy stations fill 487 of 625 cells, so the matrix is fine. A matrix grows as n², though: 500 stations means 250,000 cells (2 MB as doubles) and a 500-column table, while riders connect only a small share of pairs. The edge list (from, to, weight) has one row per pair that exists, indexes well, and joins to the node table on the station code.
