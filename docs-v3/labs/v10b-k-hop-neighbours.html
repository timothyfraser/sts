LC 01 · observe

At baseline (seed B32005, links of 80 or more rides, k = 2, dedupe on), how many stations are within 2 hops of the seed?

"Within 2 hops" counts hop 1 and hop 2 together, and counts stations, not join rows. Read "neighbours within k".
8: 3 stations at hop 1 plus 5 new ones at hop 2, which is ego_size(g, order = 2, mindist = 1). The two joins produced 14 rows (3 + 11) because some hop 2 rows land on stations already found, including the seed itself.

LC 02 · intervene

Set k = 3 and turn Dedupe off. How many intermediate rows does the recursive join produce, against how many distinct neighbours?

Compare "join rows" and "neighbours within k". Turning dedupe off changes the rows, never the set of stations reached.
Without dedupe the three joins make 3 + 11 + 58 = 72 rows, one per walk, yet they reach the same 16 stations. With dedupe on, each hop keeps only distinct stations, so the joins make 40 rows and keep 23. At k = 4 the raw walk count jumps to 311 for 17 stations; drop the threshold to 20 rides and it is 57,772 rows for 24 stations.

LC 03 · transfer

Why does counting neighbours in a database need DISTINCT or a visited set, and what does that cost at scale?

Set threshold 20, k = 4, dedupe off, and read the join counter per hop. Then switch dedupe on.
Without dedupe the rows grow roughly as degree to the power k (18, 251, 3,685, 53,818 here) while only 24 stations exist. DISTINCT, SQL's UNION or a visited set collapses each frontier to at most one row per station, so the next join starts small. The price is a hash or sort over each hop's rows and memory for the visited set, which at millions of nodes is why graph databases and igraph keep BFS state instead of re-joining.
