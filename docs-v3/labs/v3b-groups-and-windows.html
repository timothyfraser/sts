Chapter 3 · Grouped data and window functions

Groups, summaries and lags

Learning objective: Distinguish summarise, mutate and reframe on grouped data, and compute lags within groups without leaking across group boundaries.

Controls

group_by(muni_code)
Verb
Window (mutate only)
Order by date

Metrics

Legend

  • one row; colour = municipality
  • window reads a row in the same group
  • window reads a row from another municipality (leak)

LC 01 · observe

At baseline the lab runs group_by(muni_code) %>% summarize(mean_solar = mean(solar)) on 96 rows. How many rows come out?

Read "rows out" in the sidebar, and count the coloured groups left on the bench.
8. summarize collapses each group to one row, so 8 municipalities give 8 rows. Turn group_by off and the same code gives 1 row; mutate would keep all 96.

LC 02 · intervene

Choose mutate and lag with n = 1, then turn group_by off. Which rows now get a value from the wrong municipality?

Look for the red arrows and the "leaked rows" metric.
7 rows leak. Without groups, lag() walks straight down the whole table, so the first observation of each of the 7 later municipalities borrows the previous municipality's last value. Only 1 row is NA instead of 8. With n = 3 the leak grows to 21 rows.

LC 03 · transfer

In SQL you write LAG(solar, 1) OVER (PARTITION BY muni_code ORDER BY date). Why both clauses, and what goes wrong without ORDER BY?

Set group_by on, mutate, lag, and switch Order by date off. Watch the dates in each lane and the sum of the lag column.
PARTITION BY plays group_by (0 leaks); ORDER BY plays arrange(date). With order off here the rows are in stored order, so the lag sum changes from 12,541 to 12,257 even though no row leaks: each value is lagged from the wrong month.
